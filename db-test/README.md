# Transport Monitoring DB — PostgreSQL

Набор для первого рабочего цикла проектирования БД:

- `001_schema.sql` — создание PostgreSQL schemas, таблиц, FK, CHECK/UNIQUE ограничений, индексов и триггеров `updated_at`.
- `002_seed.sql` — детерминированные демонстрационные данные для разработки.
- `003_tests.sql` — автоматические проверки ограничений, связей, use cases и формы запросов worker'а.
- `004_concurrency_test.md` — ручная проверка конкурентной обработки очереди уведомлений через `FOR UPDATE SKIP LOCKED`.

## Порядок запуска

```text
001_schema.sql
      ↓
002_seed.sql
      ↓
003_tests.sql
```

Для чистой БД:

```bash
psql "$DATABASE_URL" -f 001_schema.sql
psql "$DATABASE_URL" -f 002_seed.sql
psql "$DATABASE_URL" -f 003_tests.sql
```

`003_tests.sql` завершает свою работу через `ROLLBACK`, поэтому тестовые вставки внутри него не загрязняют seed-данные.

## Что считать предметом ревью

Схема является первой версией, а не неизменным контрактом. До интеграции приложения нормально менять:

- названия таблиц/полей;
- типы данных;
- кардинальности;
- `ON DELETE` стратегии;
- индексы;
- статусные значения;
- способ хранения расписания;
- разделение на PostgreSQL schemas.

После начала интеграции любые изменения лучше оформлять отдельной migration, а не переписывать уже примененный DDL.

## Важное архитектурное ограничение

`transport` не зависит от Telegram. Telegram находится в application/bot слое. Поэтому добавление автобусов должно происходить через новую реализацию provider/API adapter, а не через копирование таблиц поездов.

## Следующий этап

После ревью этой схемы:

1. при необходимости внести изменения;
2. зафиксировать DDL как v1;
3. написать repository SQL;
4. подключить application services;
5. затем интегрировать Bot Service / Monitor Worker / Notification Worker.
